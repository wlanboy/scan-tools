# CWE-288 in Spring-Boot-REST-Services

## Worum es geht

[CWE-288](https://cwe.mitre.org/data/definitions/288.html) heißt „Authentication Bypass Using an Alternate Path or Channel“. Die Anwendung verlangt eine Anmeldung, bietet aber einen zweiten Weg zur selben Funktion, auf dem keine Prüfung stattfindet.

- **Übergeordnet:** CWE-306 (Missing Authentication for Critical Function), CWE-284 (Improper Access Control)
- **Untergeordnet:** CWE-425 (Direct Request / „Forced Browsing“)
- **Verwandt:** CWE-420 (Unprotected Alternate Channel)
- **Gegenmaßnahme laut MITRE:** jeden Zugriff durch eine einzige Kontrollstelle führen und die Berechtigung bei jedem Zugriff prüfen

Die Beispiele bei MITRE sind alt (Router, Escape-Taste an der Passwortabfrage). Für Web-Anwendungen passen CVE-2002-0870 und CVE-2003-0304 am besten: Wer eine Verwaltungs-URL direkt aufrief, bekam Rechte ohne Login.

## Kann das einen Spring-Boot-REST-Service treffen?

Ja, auf zwei Wegen:

1. **Fehler im Framework:** Spring Security entscheidet anhand von URL-Mustern, was geschützt ist. Spring MVC leitet Anfragen anhand eigener Muster an Controller weiter. Legen beide einen Pfad unterschiedlich aus, erreicht eine Anfrage den Controller, ohne dass eine Sicherheitsregel greift.
2. **Fehler in der eigenen Anwendung oder im Deployment:** vergessene Endpoints, Vertrauen in Gateway-Header, ungeschützte Nebenkanäle. Diese Fälle bekommen keine CVE-Nummer und sind in der Praxis häufiger.

## Wie schlimm ist das?

CWE-288 hat selbst keinen Score, die Schwere hängt vom konkreten Fall ab. Für die Spring-Fälle ist das Bild einheitlich:

- **Angriffsweg:** über das Netzwerk, ohne Zugangsdaten, ohne Zutun eines Nutzers (CVSS `AV:N/PR:N/UI:N`)
- **Folge:** Alles hinter der Anmeldung ist erreichbar. Je nach Endpoint heißt das Datenabfluss, Datenänderung oder Zugriff auf Admin-Funktionen.
- **Einstufung:** Spring bewertet diese CVEs als HIGH, einzelne als CRITICAL. Für CVE-2026-22733 nennt OSV einen CVSS-Score von 8.2.

Bei einem öffentlich erreichbaren Service sollte ein bestätigter Fund kurzfristig behoben werden. Ist der Service nur intern erreichbar, sinkt das Risiko, verschwindet aber nicht (siehe Gateway-Fall unten).

Dass eine Konfiguration „ungewöhnlich“ ist, sagt wenig über das Risiko. Spring schreibt zu CVE-2026-22731, das Setup komme in Produktion selten vor. Wer genau so konfiguriert hat, ist trotzdem voll betroffen.

## Spring-Advisories dieser Klasse

Die Versionsangaben stammen aus [`advisories.json`](advisories.json) (Quelle: <https://spring.io/security>). Das Feld `weakness` ist dort leer. Die Zuordnung zu CWE-288 für CVE-2026-22731 und CVE-2026-22733 stammt aus den CVE-Datensätzen bei NVD/OSV. Die übrigen Einträge folgen demselben Muster (Sicherheitsregel greift auf einem zweiten Pfad nicht), sind aber nicht offiziell als CWE-288 eingestuft.

„ent.“ bedeutet: Fix nur über Spring Enterprise Support.

### Embedded Tomcat

Spring Boot liefert Tomcat als eingebetteten Server mit. Tomcat-CVEs stehen nicht in [`advisories.json`](advisories.json), betreffen Spring-Boot-Anwendungen aber über die Abhängigkeit `tomcat-embed-core`.

| CVE | Datum | Schwere | CWE | Voraussetzung | Betroffen → behoben |
|---|---|---|---|---|---|
| [CVE-2026-68525](https://www.cve.org/CVERecord?id=CVE-2026-68525) | 2026-08-25 | Apache: LOW, CISA ADP: 9.1 CRITICAL | CWE-863 | Tomcat-FORM-Authentifizierung und ein Security-Constraint, der eine Ressource nur für POST schützt, nicht für GET. Nach dem Redirect der FORM-Anmeldung lässt sich der methodenspezifische Constraint umgehen. | 11.0.0-M1–11.0.24 → 11.0.25, 10.1.0-M1–10.1.57 → 10.1.58, 9.0.0.M1–9.0.120 → 9.0.121; 8.5.x und 7.0.x sind EOL und betroffen, ohne Fix |

Die CWE-Zuordnung lautet offiziell CWE-863 (Incorrect Authorization), nicht CWE-288. Das Muster ist aber dasselbe: Eine Regel gilt nur für einen Weg (POST), ein anderer Weg zur selben Ressource bleibt offen.

Für typische Spring-Boot-REST-Services ist das Risiko gering. Die Lücke liegt in Tomcats eigener, containerverwalteter FORM-Anmeldung mit `<security-constraint>` in `web.xml` oder `@ServletSecurity`. Spring Security nutzt diesen Mechanismus nicht, sondern prüft in der eigenen Filterkette. Die beiden Bewertungen gehen weit auseinander: Apache stuft die Lücke als LOW ein, CISA ADP mit CVSS 9.1. Weder das Advisory noch der CVE-Datensatz nennen Workarounds.

Den eingebetteten Tomcat trotzdem aktualisieren. Bis eine Spring-Boot-Version mit dem gefixten Tomcat verfügbar ist, lässt sich die Version in Maven über die Property überschreiben:

```xml
<properties>
    <tomcat.version>11.0.25</tomcat.version> <!-- bzw. 10.1.58 für Tomcat 10.1 -->
</properties>
```

## Typische Ursachen in der eigenen Anwendung

- **Nur das API-Gateway prüft die Anmeldung.** Der Service vertraut einem Header wie `X-User-Id`. Ist der Pod im Cluster oder über einen NodePort direkt erreichbar, setzt ein Angreifer den Header selbst. Das ist das klassische CWE-288-Muster bei Microservices.
- **Alte API-Versionen.** `/api/v2/...` ist geschützt, `/api/v1/...` läuft noch mit schwächeren Regeln. OWASP führt das als API9:2023 „Improper Inventory Management“.
- **Infrastruktur-Endpoints mit `permitAll()`:** Actuator (`/actuator/env`, `/actuator/heapdump`), H2-Console, Swagger-UI, Debug-Controller.
- **Separater Management-Port** (`management.server.port`) ohne eigene Security, in der Annahme, dass ihn niemand erreicht.
- **Lücken in den Regeln:** Nur `requestMatchers(HttpMethod.GET, ...)` ist abgesichert, andere HTTP-Methoden fallen durch. Oder `/admin` und `/admin/` werden unterschiedlich behandelt (in älteren Versionen relevant).
- **Andere Kanäle zur selben Logik:** WebSocket-, gRPC- oder Message-Listener (Kafka, RabbitMQ), die dieselbe Service-Methode aufrufen wie der REST-Controller, aber ohne Prüfung.

## Gegenmaßnahmen

1. **Aktuell bleiben:** Spring Boot mindestens 3.5.12 bzw. 4.0.4, Spring Security 7.0.5 oder neuer, wenn 7.x im Einsatz ist. Den eingebetteten Tomcat mindestens auf 11.0.25 bzw. 10.1.58 bringen (CVE-2026-68525).
2. **Standardmäßig verweigern:** Am Ende der Regeln immer `.anyRequest().authenticated()` (oder `.denyAll()`), `permitAll()` nur für ausdrücklich benannte Pfade.
3. **Zusätzlich auf Methodenebene prüfen:** `@EnableMethodSecurity` mit `@PreAuthorize` an Service-Methoden. Dann greift die Prüfung auch, wenn das URL-Matching versagt oder die Logik über einen anderen Kanal aufgerufen wird. Spring empfiehlt das schon im Advisory zu CVE-2016-5007.
4. **Jeder Service prüft den Token selbst** (z. B. JWT per `oauth2ResourceServer()`), statt einem Header vom Gateway zu vertrauen. Ergänzend NetworkPolicies, damit Pods nur vom Gateway erreichbar sind.
5. **Keine eigenen Endpoints unter Actuator-Pfaden** (`/actuator/**`, `/cloudfoundryapplication/**`, Health-Group-Pfade). Actuator nur mit den nötigen Endpoints freigeben und ebenfalls absichern.
6. **Testen:** pro geschütztem Endpoint ein Integrationstest, der ohne Token 401 erwartet. Dazu Varianten mit Slash am Ende, URL-Encoding, anderen HTTP-Methoden und Servlet-Pfad-Präfix.

Beispiel für eine Filterkette mit Default-Deny:

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/health").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()));
    return http.build();
}
```
